Case Study · OPSM (On-Prem Sales Management)

harness 工程贯穿全 SDLC harness エンジニアリングで SDLC を貫く Harness Engineering Across the Full SDLC

在「定制 Claude Code」之上，给 LLM 套上一整套 harness（feed-forward 规则/技能/规格 + feedback 传感器 lint/test/review/CI），让每个阶段都被强制遵守——这才是「保证效果」的来源。本案例以一套通用的、匿名的オンプレ販売管理系统（OPSM）为载体演示。 「Claude Code をカスタマイズ」した上で、LLM に harness（feed-forward：ルール/技能/仕様 ＋ feedback：lint/test/review/CI）を被せ、各フェーズで強制遵守する。これが「効果を担保する」根拠。本事例は汎用・匿名のオンプレ販売管理システム（OPSM）で示す。 On top of "customizing Claude Code," we wrap a full harness (feed-forward rules/skills/specs + feedback sensors lint/test/review/CI) around the LLM so that every phase is enforced. This is where "guaranteed effect" comes from. The case is illustrated with a generic, anonymous on-prem sales management system (OPSM).

Two Notes Up Front

先讲两点最初に 2 つTwo Things First

① 技术栈是「预设」技術スタックは"仮置き"The Stack is a Placeholder

Python / FastAPI / PostgreSQL 只是为演示流程随意选的组合。真实项目应在动工前与 AI 协作，依据团队技能、既有系统、合规、运维约束共同选型——这一步本身也是 harness 的一环。 Python / FastAPI / PostgreSQL は流れを見せるために選んだだけ。実プロジェクトでは着手前に AI と相談し、チーム技能・既存資産・コンプラ・運用制約に応じて共同で選定する——選定自体が harness の一部。 Python / FastAPI / PostgreSQL is just a convenient combo for demonstration. Real projects must consult AI up front and pick the stack jointly based on skills, legacy assets, compliance, and ops constraints — that decision is itself part of the harness.

② 本工程是「简版」本工程は"簡略版"This Sample is Trimmed

harness 件齐全但内容是简版（规约 / 清单 / 观点都精简）。真实工程应按团队 process（评审流程、合规、分支策略、发布节奏、审批等）适当扩充。 harness 一式は揃えたが内容は簡略版（規約・チェックリスト・観点はいずれも精錬）。実工程は各社 process（レビュー手順・分岐戦略・リリース・承認 等）に合わせて拡張すること。 All harness pieces are present but their content is trimmed. Real projects must extend them to match each team's process (reviews, branches, releases, approvals, compliance).

# demo/.claude/hooks/no-external-net.sh（抜粋）
if printf '%s' "$cmd" | grep -Eq '(curl|wget|nc|ssh|scp|pip[0-9]* +install|npm +install)'; then
  if printf '%s' "$cmd" | grep -Eqv '(localhost|127\.0\.0\.1|::1|10\.|192\.168\.|172\.(1[6-9]|2[0-9]|3[0-1])\.)'; then
    echo "[no-external-net] オンプレ制約：外部ネットワークへの接続は禁止です → $cmd" >&2
    exit 2   # ← Claude Code はこのコマンドを実行できない
  fi
fi

1. docs/specs/order.md — 受容基準（抜粋）

## 4. 受容基準（Acceptance Criteria）
1. AC-1: 受注は最低 1 件の明細を持つ。空の明細での確定は不可。
2. AC-2: 数量は 1 以上の整数。
3. AC-4: 受注合計 = Σ(明細.単価 × 明細.数量)。
5. AC-5: 状態遷移は draft → confirmed → shipping → completed、各状態から cancelled も可（completed からのキャンセル不可）。
6. AC-6: 合計 ≥ 1,000,000 円は requires_approval=True、未承認では confirm 不可。
8. AC-8: 確定操作は冪等。

2. src/app/domain/order.py — 純 Python ドメイン

def confirm(self, approved: bool = False) -> None:
    """draft → confirmed（AC-1, AC-5, AC-6, AC-8 冪等）。"""
    if self.status is OrderStatus.CONFIRMED:
        return  # AC-8: 冪等
    if self.status is not OrderStatus.DRAFT:
        raise OrderInvariantError(...)  # AC-5
    if not self.lines:
        raise OrderInvariantError("明細が空の受注は確定できません（AC-1）")
    if self.requires_approval() and not approved:
        raise OrderInvariantError("高額受注は承認が必要です（AC-6）")
    self.status = OrderStatus.CONFIRMED

3. tests/test_order_domain.py — 受容基準＝テスト

# AC-6 高額受注は承認必須
def test_ac6_high_value_requires_approval() -> None:
    order = Order(id="O-1", customer_id="C-1")
    order.add_line(_line(quantity=1, unit_price=1_000_000))
    assert order.requires_approval() is True
    with pytest.raises(OrderInvariantError):
        order.confirm()                      # 未承認は不可
    order.confirm(approved=True)
    assert order.status is OrderStatus.CONFIRMED
