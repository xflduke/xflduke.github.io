# 仕様：受注（Order） — 貫通実装対象

> 教学用の簡版。実プロジェクトでは業務フロー / 帳票 / 承認権限などをさらに詳述すること。

## 1. 目的
顧客からの注文を受け付け、確定 → 出荷準備 → 完了 までの状態を管理し、在庫・請求と連携する基盤を提供する。

## 2. スコープ
### やる
- 受注の作成・確定・キャンセル・完了。
- 受注明細（商品・数量・単価）の管理。
- 合計金額の計算（明細小計の合算、税抜）。
- 高額受注の承認フラグ判定（閾値: 1,000,000 円）。

### やらない（本サンプルでは）
- 多通貨対応 / 値引きルール / 与信管理 / 出荷物流連携。
- 帳票出力（PDF）。

## 3. ユーザーストーリー
- 営業担当として、顧客からの注文を入力し、確定したい。
- 営業マネージャとして、高額受注の承認フローを通したい。
- 倉庫担当として、確定済みの受注を出荷準備状態に進めたい。

## 4. 受容基準（Acceptance Criteria）
1. **AC-1**: 受注は最低 1 件の明細を持つ。空の明細での確定は不可。
2. **AC-2**: 数量は 1 以上の整数。0 や負値は不可（`OrderInvariantError`）。
3. **AC-3**: 単価は 0 以上の整数（円）。負値は不可。
4. **AC-4**: 受注合計 = Σ(明細.単価 × 明細.数量)。
5. **AC-5**: 状態遷移は次のみ許可：
   `draft → confirmed → shipping → completed`、各状態から `cancelled` も可（completed からのキャンセル不可）。
6. **AC-6**: 合計金額が 1,000,000 円以上の受注は `requires_approval=True` となり、承認なしに `confirmed` へ遷移できない。
7. **AC-7**: 一度確定（`confirmed` 以降）した受注の明細は変更不可（不変条件）。
8. **AC-8**: 同一 ID への確定操作は冪等（再度呼んでも例外にならず、状態は変わらない）。

## 5. ドメインルール / 不変条件
- 明細リストは空にならない（`confirmed` 以降）。
- 合計金額は明細から導出する派生属性（保存しない）。
- 状態は `OrderStatus` Enum で表現。

## 6. オンプレ制約への影響
- 受注データは構内 PostgreSQL に保存。外部 SaaS 連携なし。
- 承認通知は構内メールサーバ経由（本サンプルでは未実装）。

## 7. 未決事項
- 値引き / 税計算 / 通貨は将来課題。
- 承認者ロールの厳密モデル化は本サンプル範囲外。
